# 线上运维

## 出事时的顺序

**先止血，再看根因。** 顺序不能反：

1. 确认影响面：几个人受影响？还在扩大吗？
2. 立刻能做的缓解：回滚、切流、限流、重启（重启前先留证据）
3. 通知：谁在用、谁在修、什么时候给下一次更新
4. 找根因
5. 写复盘

第 2 步里，重启最容易做，也最容易把证据冲掉。重启之前至少抓一次：`top`、`df -h`、最近的错误日志、连接数。

## 排障看什么

按这个顺序看，不要随机猜：

| 现象 | 先看 |
| --- | --- |
| 打不开 / 502 | 进程还在吗、端口通吗、上游健康检查 |
| 慢 | 响应时间分布（P50 还是 P99 慢）、慢查询、连接池、GC |
| CPU 高 | 哪个进程、哪个线程、是计算还是空转 |
| 内存涨 | 是缓存还是泄漏，涨的速度 |
| 磁盘满 | 谁占的、日志有没有滚动、临时文件 |

同一时间只改一个变量。同时改三处，问题消失了也不知道是哪一处修好的。

## 告警怎么设才不吵

只有满足下面条件的才告警：

- 用户能感觉到（错误率、可用性、关键接口的延迟）
- 有人能立刻处理
- 有明确的处理动作

不要告警：

- 单机 CPU 瞬时高
- 单次请求超时
- 可以自动恢复的抖动

告警值设一个「通知」线和一个「叫醒」线。所有事都叫醒，等于没有告警。

## 服务器基线

新机器上线前，至少做到：

- 只开需要的端口，默认拒绝
- 不用密码登录，用密钥
- 关闭 root 直接登录
- 时区、时间同步
- 日志滚动，磁盘不会被写满
- 有备份，且**备份能恢复**

最后一条要真跑一次恢复。没恢复过的备份不算备份。

## 容量怎么判断

别看平均值。看峰值，看增长：

- 当前峰值是多少，容量是多少
- 最近的增长速度
- 什么事件会让它突然翻倍

峰值到 70% 就该准备扩容，不要等到 95%。

## 复盘

只写事实，不写情绪：

```
什么时候发现、怎么发现的
影响：多久、多少人、什么事做不了
过程：每一步做了什么，几点几分
原因：直接原因 / 根本原因
改：谁在什么时候改什么
```

「人为失误」不是根本原因。人为什么会那么做，才是。

## 常见错误

- **上来就重启**：故障暂时消失，明天再来一次。
- **告警全开**：一天两百条，没人看。
- **备份没试过恢复**：出事时才发现备份是空的。
- **复盘只写原因不写改动**：同样的故障会再来一次。
