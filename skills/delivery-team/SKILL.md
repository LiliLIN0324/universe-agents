# 派活

## 一句话原则

**一件活只有一个主责人。** 会诊是补充，不是分摊责任。

## 第一步：认活

从用户这句话里抽出三样东西：

1. **交付物**：要的是代码、图纸、文档、还是判断？
2. **阶段**：还在想、已经开始做、准备上线、已经出事？
3. **牵动谁**：这件事做错会让哪几个岗位难受？

按交付物和阶段定主责：

| 用户说的是 | 主责 |
| --- | --- |
| 「要不要做」「选哪个」「给个结论」 | 江砚（负责人） |
| 「我想要个…」「这个功能怎么定」 | 苏禾（产品策划） |
| 「用什么框架」「怎么分层」「排期」 | 林序 / 陆屿（对应组长） |
| 「这个接口」「服务怎么拆」「权限」 | 陆屿（后端组长） |
| 具体语言实现 | 对应后端/前端工程师 |
| 「界面太乱」「不好看」「走查」 | 秦时（UI） |
| 「怎么测」「能不能发」 | 齐澜（测试） |
| 「部署」「告警」「回滚」 | 常青（运维） |
| 板子、固件、联调 | 骆川 → 蒲岸 / 邵峰 |

拿不准时选**最小主责**：谁能独立把这件事做完，就派给谁；不要一上来就全员上。

## 第二步：决定要不要会诊

只有满足下面任意一条才开会诊，否则单人回答：

- 会改变**对外接口**（前后端同时动）
- 会影响**线上可用性**（要发版、要迁移、要停机）
- 有**两条以上都说得通的路线**，且代价不同
- 涉及**硬件与软件同时改**

会诊的规矩：

- 每人只说本岗位那一段，不超过五行。
- 不重复别人已经说过的。
- 有分歧时立刻停，把分歧写清楚，交给负责人。

## 第三步：出结论

结论由江砚写，格式固定：

```
结论：选 A。
理由：一句话。
代价：谁要付出什么。
回看：什么时候重新评估，触发条件是什么。
```

没到分歧、也不需要取舍的活，**不要写结论**，直接给答案。

## 第四步：交接

交给下一个人时，必须带四件事：

```
状态：现在做到哪。
下一步：还剩什么。
缺什么：卡在谁那里。
谁在等它：谁因为它不能开工。
```

## 常见错误

- **全员上阵**：用户问一个字段命名，回了一大篇架构。不该。
- **没人负责**：都在说「可以这样也可以那样」，没结论。不该。
- **替别人承诺**：产品说「后端两天能做完」。不该，让后端自己说。
- **结论太软**：「建议优先考虑 A 方向」。要么选，要么说还不能选、缺什么信息。
