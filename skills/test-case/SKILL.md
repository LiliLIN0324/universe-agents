# 用例设计

## 一条需求至少四个用例

任何一条验收标准，起步就是四个：

1. 正常输入，得到预期结果
2. 边界上的值，得到预期结果
3. 非法输入，得到明确拒绝
4. 什么都不填 / 少一步操作

只写第 1 条的测试，等于没测。

## 边界值从哪来

先找输入里的「临界点」：

- 数量：0、1、最大值、最大值 + 1
- 长度：空、1 个字、上限、上限 + 1
- 金额：0、0.01、整数、小数两位以上、负数
- 时间：今天、昨天、跨月、跨年、闰日
- 文件：0 字节、刚好上限、超上限、错误格式

取「临界点本身」和「临界点前后各一个」。这三刀最关键。

## 等价类：不要穷举

一百个数字输入，不用测一百个。分成几组，每组挑一个代表：

| 组 | 例子 | 挑哪个测 |
| --- | --- | --- |
| 合法范围 | 1–100 | 50（中间） |
| 下界外 | 0 | 0 |
| 上界外 | 101 | 101 |
| 非数字 | 字母、空、符号 | 各一个 |

一个组内如果结果一致，测一个就够了；如果不一致，说明分组分错了，要重分。

## 状态怎么测

有状态的流程，按「迁移」测，不按「页面」测：

1. 列出所有状态
2. 列出每个状态能去哪
3. 每条边至少一条用例
4. 再补两条：不该发生的迁移、和从中间状态直接退出

例：草稿 → 提交 → 审核 → 通过 / 退回。要测的不只是「能通过」，还有「审核中能不能改」「退回后再提交会不会重复」。

## 参数化写法

同样的逻辑、不同的数据，写成一张表，不要复制十遍：

```
用例编号 | 输入 | 期望 | 覆盖点
TC-01    | 50   | 通过 | 合法中间值
TC-02    | 0    | 拒绝 | 下界外
TC-03    | 101  | 拒绝 | 上界外
TC-04    | abc  | 提示格式错误 | 非数字
```

表的每一行都是一条独立用例，能单独跑、单独标记通过与否。

## 追溯

每条用例标上它验的是哪条验收标准：

```
TC-02 ← AC-3：范围 1–100，超出时要提示
```

没挂到任何标准的用例，要么是漏写的标准，要么是没用的用例。趁早发现。

## 执行结果只写三种

- **通过**：实际和期望一致
- **不通过**：附实际结果
- **未执行**：附原因

不要写「基本通过」「有点问题」。这种记录在复盘时毫无用处。

## 常见错误

- **只测显眼的那条路**：最难测的那条才最容易出问题。
- **用例写得像文档**：一条用例一段话，执行时还在读。一条用例三行以内。
- **没有前置条件**：用例没说从哪个状态开始，结果没法复现。
- **测完不改**：需求变了，用例还是老的，后面全在验过去的东西。
