# 发布流水线

## 流水线分四段

| 段 | 做什么 | 失败怎么办 |
| --- | --- | --- |
| 构建 | 装依赖、编译、打制品 | 停，不进入下一段 |
| 验证 | 类型检查、单测、镜像扫描 | 停，修复后重跑 |
| 预备 | 传到目标环境、跑迁移、预热 | 停，环境保持原样 |
| 切换 | 切流量、改指针、重启 | 按预案回滚，不现场调试 |

每段都要能独立重跑。最怕的是「重跑一次就从搭环境开始」。

## 制品要不可变

一次构建，处处使用同一个制品：

- 制品带版本号和提交哈希
- 同一个制品先上预发，再上生产
- **不要在发布机上重新构建**。重新构建出来的东西，和测过的不是一个东西。

版本号规则写清楚。出现「latest」这个标签，就说明没人能说清线上跑的是哪一版。

## 发布方式怎么选

| 方式 | 适合 | 代价 |
| --- | --- | --- |
| 全量替换 | 内部工具、能随时停 | 有停机 |
| 滚动 | 常见的 Web 服务 | 新旧版本同时在线，接口要兼容 |
| 蓝绿 | 要秒级回滚 | 资源翻倍 |
| 灰度 | 用户量大、变更风险高 | 要能按比例或按人分流 |

选了滚动，就意味着这一版和下两版之间**接口要兼容**。这条经常被忘。

## 回滚必须验证过

回滚方案写在纸上不算数。上线前要实测一次：

1. 切到新版本
2. 立刻切回旧版本
3. 确认业务正常

没做过这一步的「回滚方案」，在真出事的时候大多不可用。

数据库变更要特别小心：**加了字段能回滚，删了字段不能**。所以：

- 先加新字段，双写，读新
- 过一段时间确认没人读旧字段
- 再删旧字段

三步分开上线，不要一次做完。

## 配置跟着版本走

配置不是代码之外的零碎。规则：

- 所有环境的配置都进仓库（敏感值用密钥管理，不放仓库）
- 配置缺项时**启动失败**，不要用默认值悄悄跑起来
- 每次发布记录改了哪些配置项

用默认值兜底，是生产事故最常见的来源之一。

## 上线后十分钟

自动看三样：

1. 错误率有没有跳
2. 关键接口的响应时间
3. 有没有新的异常日志类型

十分钟内发现问题，回滚代价最小。过了半小时再来，就要连带处理用户投诉。

## 常见错误

- **流水线只看构建成功**：构建绿了，线上炸了。
- **手动改线上配置**：下次发布全被覆盖，问题复现不了。
- **回滚要重跑流水线**：太慢，出事时来不及。
- **发布不通知**：周边服务的同事不知道你在发，看到报错先在群里喊。
