# 质量把关

## 先分清楚测什么

不是所有东西都值得测到同一个程度。按「坏了会怎样」分级：

| 级别 | 标准 | 测法 |
| --- | --- | --- |
| A 不能坏 | 坏了用户流失、数据丢、钱算错 | 每次发版全测，人工 + 自动 |
| B 坏了麻烦 | 功能不可用但有替代路径 | 每次发版冒烟，改动处细测 |
| C 坏了能忍 | 体验瑕疵 | 发版前抽查 |

分级表要先写出来。没分级，就会变成「全都重要」，最后等于都不重要。

## 质量红线

下面这些一旦出现，**不看进度、不谈权衡，直接不发**：

1. 数据丢失或写错，且无法恢复
2. 权限越界：能看见或改动别人本不该看的东西
3. 密钥、口令出现在前端、日志、截图里
4. 主流程走不完
5. 已知崩溃，且能稳定复现
6. 回滚方案没验证过

红线是事先定的，不是出事时商量的。

## 测试计划怎么写

一页纸就够，四块：

```
范围：这版改了什么，连带影响什么
不测：明确不覆盖的部分，和原因
环境：在哪测，数据从哪来，账号怎么准备
判定：什么算通过，谁签字
```

「不测」这一栏最重要。写清楚不测什么，比写清楚测什么更能避免扯皮。

## 回归范围怎么定

不按「全部重测」，按影响链：

1. 改了哪些文件 / 接口
2. 谁调用这些接口
3. 这些调用方所在的页面
4. 这些页面共用的组件

四条顺着走一遍，就是回归范围。走不到的，不测。

## 自动化测什么

适合自动化：

- 每次都要跑的冒烟路径
- 接口契约（字段、状态码、错误结构）
- 计算逻辑（金额、面积、日期）

不适合自动化：

- 一次性的活动页
- 视觉细节
- 还没定下来的需求

覆盖率不是目标。把覆盖率写到 90% 而冒烟路径没跑通，等于零。

## 缺陷怎么记

一条缺陷要能被别人复现：

```
环境：
步骤：
实际：
期望：
```

四样缺一，退回去让提的人补。不接受「这个功能有问题」这种条目。

## 放行结论只有三种

- **发**：红线全过，B 级问题有明确延期计划
- **带条件发**：不影响主流程的问题已知、已告知、有兜底
- **不发**：有任何一条红线

不要出现「应该没问题」。说不清就是不发。

## 常见错误

- **测了个寂寞**：测试用例全绿，但用户走的路没人走过。
- **拿覆盖率当结论**：数字好看，主流程有坑。
- **发版前一天才开始测**：来不及，只能放行。
- **缺陷描述靠截图**：截图看不出步骤，别人复现不了。
