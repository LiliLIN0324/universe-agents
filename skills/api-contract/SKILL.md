# 接口契约

## 顺序不能反

**先写契约，再写实现。** 前端拿着契约就能开工，后端照着契约实现，测试照着契约写用例。

## 一、先定这六项

1. **路径与方法**：资源用名词复数，动作靠 HTTP 方法表达。
2. **入参**：字段名、类型、是否必填、取值范围。
3. **出参**：成功长什么样，最小可用字段有哪些。
4. **错误码**：业务错误用统一结构，不要返回 200 带 `success:false` 又不给码。
5. **权限**：谁能调，越权返回什么（统一 403，不泄露资源是否存在）。
6. **幂等**：哪些写操作必须可重试。

## 二、错误结构统一

```json
{ "code": "SEAT_TAKEN", "message": "座位已被占用", "field": "seatId", "requestId": "..." }
```

- `code` 给机器看，稳定不变。
- `message` 给人看，可以改文案。
- `field` 可选，表单字段错时用。
- `requestId` 用来对日志。

## 三、破坏性变更的判定

以下任一即为破坏性，**必须升版本并提前通知**：

- 删字段、改字段名、改字段类型
- 把可选变必填
- 收紧取值范围
- 改变错误码含义
- 改变默认排序或分页行为

新增可选字段、新增接口不是破坏性变更。

## 四、联调前的自检

- [ ] 契约文件能通过校验
- [ ] 有至少一个成功示例和一个失败示例
- [ ] 分页参数与返回结构写清楚（总数？游标？）
- [ ] 时间格式、时区、精度写清楚
- [ ] 空值与缺字段的区别写清楚
- [ ] 限流与超时写了预期值

## 五、Mock 的用法

契约定完先出 mock，前端先跑起来。mock 必须由契约生成，**不许手写一份和契约不一致的假数据**，否则联调时才发现字段对不上。

## 输出格式

> **契约**：路径、入参、出参、错误码。
> **破坏性**：有 / 无；若有，影响哪些调用方。
> **联调**：谁先接、mock 什么时候撤。
> **测试**：需要覆盖哪几条错误路径。
