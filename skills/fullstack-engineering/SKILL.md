# 前后端工程

## 先定边界

一个功能开做之前，三件事必须先定：

1. **数据长什么样**：接口返回什么字段
2. **谁负责算**：某个值由前端算还是后端算
3. **错误怎么传**：出错了返回什么、页面显示什么

这三件没定，两个人都开始写，最后一定要返工。

判断「谁负责算」：**能影响数据正确性的，一律后端算。** 金额、权限、可用性、数量限制，前端只显示，不裁决。

## 分层

后端：

```
入口层：收请求、校验入参、鉴权
业务层：规则与流程，不碰数据库
数据层：查询与写入，不含业务判断
```

跨层的调用只允许相邻。业务层直接写 SQL，短期快，三个月后改不动。

前端：

```
页面：路由与布局
容器：取数据、管状态
组件：只接收 props，渲染
```

一个组件同时负责取数据和渲染，就没办法复用了。这条判断标准比任何目录规范都实用。

## 状态放哪

- 只在一个页面用的：放页面
- 跨页面共享的：放全局，但要少
- 服务端来的数据：不要自己复制一份长期保存，容易和真数据不一致
- 能从别的状态算出来的：不要再存一份

「两份状态要手动保持同步」，几乎一定会不同步。

## 接口约定

一个字段，两种状态：

```json
{
  "code": "VENUE_TOO_LARGE",
  "message": "场地超出限制",
  "data": null
}
```

规矩：

- 错误用**机器可读的 code**，不要只给人看的 message。
- 前端按 code 分支，不按 message 文案判断。
- 空结果和失败要能分清：`data: []` 和 `code: NOT_FOUND` 是两回事。
- 时间统一用带时区的 ISO 格式，不要各写各的。

## 联调顺序

1. 接口先定，写一份示例响应（假的也行）
2. 前端按示例做页面
3. 后端按约定实现
4. 两边一起对

第 1 步花半小时，能省下后面两天。跳过这步，联调时最常见的争论是「我以为你会返回空数组」。

## 提交前自检

- [ ] 类型检查通过，没有跳过的报错
- [ ] 新加的路径有测过：正常、空、出错
- [ ] 没有把密钥、地址、调试代码提交上去
- [ ] 日志里不打印用户敏感信息
- [ ] 改动范围之外的代码没有被顺手格式化

最后一条：顺手格式化会让 diff 变得没法看，评审的人找不到你真正的改动。

## 常见错误

- **前后端各留一份校验**：两边规则不一致，前端拦住的走后端放过去了。
- **为了让页面先跑起来，前端自己造假数据**：后来忘了，上线还在显示假数据。
- **一个接口没有错误分支**：出错时页面白屏。
- **大改动混在小修复里**：出问题回滚不了。
